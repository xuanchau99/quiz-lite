🌟 PHẦN 1: THUYẾT TRÌNH (SLIDES/TỔNG QUAN)

  • Chào hỏi:
    "Chào mọi người, hôm nay em xin phép trình bày về dự án Quiz Lite - Hệ Thống Thi Trắc Nghiệm Hiệu Suất Cao."
  • Vấn đề (Pain-point):
    "Trong thực tế, các kỳ thi tập trung thường có hàng ngàn học sinh cùng truy cập và thao tác (chọn đáp án, nộp bài) cùng một thời điểm. Điều này dễ dẫn đến nghẽn mạng và sập Database nếu chúng ta chỉ dùng các kỹ thuật CRUD thông thường."
  • Giải pháp:
    "Để giải quyết bài toán này, Quiz Lite được thiết kế với kiến trúc tối ưu để chịu tải cực cao, kết hợp xử lý bất đồng bộ và lưu trữ tạm thời siêu tốc, đồng thời tích hợp thêm AI để hỗ trợ giảng viên."

2. Kiến Trúc & Công Nghệ Cốt Lõi (2 phút)

  • Core Backend: Java 17 + Spring Boot 3.x.
  • Database tối ưu: PostgreSQL với kiểu dữ liệu JSONB giúp lưu trữ cấu trúc câu hỏi linh hoạt.
  • Xử lý chịu tải cao: Sử dụng Redis lưu trữ dạng Hash (O(1)) để Auto-save đáp án học sinh mà không làm thắt cổ chai Database.
  • Xử lý bất đồng bộ: Sử dụng RabbitMQ để đưa việc chấm điểm vào hàng đợi (queue), giúp hệ thống phản hồi mượt mà.
  • Real-time: Thông báo điểm số ngay lập tức qua WebSocket (STOMP) sau khi RabbitMQ xử lý xong.
  • AI: Tích hợp Google Gemini API tự động sinh bộ câu hỏi trắc nghiệm.

⚖️ PHẦN 2: ĐÁNH GIÁ ĐIỂM MẠNH & ĐIỂM YẾU

✅ Điểm mạnh của hệ thống

  • Chịu tải cực tốt (High-throughput): Sử dụng Redis để lưu bộ nhớ đệm (In-memory Cache) thay vì ghi trực tiếp xuống Database, loại bỏ hoàn toàn rủi ro quá tải DB khi hàng ngàn thí sinh click chọn đáp án cùng lúc.
  • Luồng xử lý Non-blocking: Nhờ Message Broker (RabbitMQ), việc nộp bài và chấm điểm được tách rời. API trả về phản hồi tức thì (202 ACCEPTED), mang lại trải nghiệm người dùng không độ trễ.
  • Cấu trúc dữ liệu linh hoạt: Áp dụng `JSONB` của PostgreSQL giúp dễ dàng thiết kế các loại câu hỏi đa dạng (Multiple choice, Điền từ, Kéo thả...) trong tương lai mà không cần thay đổi cấu trúc bảng (Schema).
  • Bắt kịp xu hướng công nghệ: Tích hợp mượt mà với Generative AI (Google Gemini) giải quyết bài toán ra đề nhanh cho giáo viên.

🚧 Điểm yếu và Hướng cải thiện

  • Thiếu cơ chế Read-Cache: Hệ thống hiện tại dùng Redis rất tốt cho luồng Ghi (Auto-save). Tuy nhiên, ở luồng Đọc (Lấy danh sách đề thi, lấy chi tiết hàng trăm câu hỏi), hệ thống vẫn đang query thẳng vào DB. (Hướng cải thiện: Cần implement Redis Cache thêm cho API lấy đề thi).
  • Single Point of Failure (Điểm chết độc nhất): Hiện dự án đang deploy theo mô hình Docker Compose đơn giản trên 1 node. Nếu Redis hoặc RabbitMQ sập, toàn bộ tiến trình thi sẽ đứt gãy. (Hướng cải thiện: Cần cấu hình Redis Cluster và RabbitMQ Cluster).
  • Khả năng theo dõi (Monitoring): Chưa có dashboard giám sát hệ thống thời gian thực. (Hướng cải thiện: Cần tích hợp Prometheus + Grafana để giám sát lượng Memory của Redis và độ dài Queue của RabbitMQ).
  • Kiến trúc nguyên khối (Monolith): Dù xử lý tốt nhưng vẫn là Monolith. Để chịu tải thực sự quy mô lớn (hàng triệu user), cần tách thành Microservices (VD: Quiz Service riêng, Grading Service riêng) và chạy trên Kubernetes (K8s).

💻 PHẦN 3: KỊCH BẢN DEMO THỰC TẾ (HANDS-ON DEMO)

Kịch bản 1: Xác thực & Phân quyền

  • Thao tác: Đăng nhập với tài khoản Admin và User.
  • Thuyết minh:
    "Hệ thống dùng JWT Stateless bảo mật. Dữ liệu được cô lập (Data Isolation) qua `@PreAuthorize` - User chỉ xem được kết quả thi của mình, Admin thì xem được tất cả."

Kịch bản 2: Admin tạo đề thi bằng AI

  • Thao tác: Đăng nhập Admin -> Vào giao diện tạo đề thi -> Nhập yêu cầu (VD: "Tạo 5 câu hỏi về Lịch sử Việt Nam") -> Bấm Generate.
  • Thuyết minh:
    "Hệ thống tự động gọi API đến Google Gemini, bóc tách chuỗi JSON trả về và lưu vào DB. API Key được bảo mật an toàn trong Database chứ không hardcode."

Kịch bản 3: Auto-save chống nghẽn (Redis High-Throughput)

  • Thao tác: Đăng nhập User -> Làm bài thi -> Click chọn các đáp án liên tục. Mở màn hình console của Redis để show dữ liệu đang được lưu vào bộ nhớ.
  • Thuyết minh:
    "Khi hàng ngàn học sinh chọn đáp án, hệ thống tuyệt đối không gọi UPDATE xuống DB. Toàn bộ thao tác ghi thẳng vào bộ nhớ RAM qua Redis Hash (O(1)). Nhờ đó, ứng dụng đạt tốc độ mili-giây và bảo vệ DB."

Kịch bản 4: Nộp bài bất đồng bộ & Real-time WebSocket

  • Thao tác: Bấm nộp bài (Submit) -> Màn hình báo nộp thành công tức thì -> 1-2 giây sau popup (Toast) báo điểm hiện lên góc màn hình.
  • Thuyết minh:
    "API lập tức trả về phản hồi không bắt đợi chấm điểm. Một Event đã được đẩy vào RabbitMQ. Ở background, hệ thống lấy ra chấm, và khi xong, kết quả được bắn về giao diện người dùng qua WebSocket để báo điểm real-time."

Kịch bản 5: Tối ưu JPA (EntityGraph)

  • Thao tác: Xem lại chi tiết bài làm đã chấm. Show một chút code Repository để chứng minh tối ưu N+1.
  • Thuyết minh:
    "Toàn bộ chi tiết được lưu bằng kiểu dữ liệu JSONB. Khi load đề thi với hàng trăm câu hỏi, em đã fix triệt để lỗi N+1 Query phổ biến của JPA bằng `@EntityGraph`, đảm bảo chỉ có 1 câu query duy nhất chạy xuống DB."
