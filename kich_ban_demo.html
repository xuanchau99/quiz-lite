QUIZ LITE SYSTEM

Kịch Bản Thuyết Trình & Phân Tích Kỹ Thuật Chuyên Sâu

Báo cáo năng lực chịu tải, đánh đổi kiến trúc (Trade-offs) và kịch bản thực chiến

PHẦN 1: THUYẾT TRÌNH TỔNG QUAN (3 PHÚT)

1. Đặt Vấn Đề & Thách Thức Kỹ Thuật (Pain-points)

  • Mở đầu & Bối cảnh:
    "Kính chào Ban giám khảo/Anh chị, hôm nay em xin đại diện nhóm trình bày về dự án Quiz Lite - Hệ Thống Thi Trắc Nghiệm Hiệu Suất Cao.

    Trong thực tế, khi tổ chức một kỳ thi tập trung cho hàng ngàn thí sinh, vấn đề lớn nhất không nằm ở tính năng CRUD cơ bản, mà nằm ở hiện tượng thắt cổ chai cơ sở dữ liệu (I/O Bottleneck) và nghẽn luồng xử lý (Thread Pool Exhaustion). Nếu cứ mỗi lần thí sinh chọn một đáp án lại phát sinh lệnh UPDATE trực tiếp xuống Database, máy chủ RDBMS chắc chắn sẽ rơi vào tình trạng Disk I/O 100%, gây giật lag và nguy cơ làm sập kỳ thi."
  • Giải pháp kiến trúc:
    "Để hóa giải triệt để bài toán này, Quiz Lite được xây dựng dựa trên 3 trụ cột kiến trúc cốt lõi:
    1. Tách rời luồng ghi (Decoupled Writes): Đệm toàn bộ thao tác chọn đáp án trên bộ nhớ RAM bằng Redis Hash O(1).
    2. Chấm điểm bất đồng bộ (Asynchronous Event-driven): Đẩy bài nộp vào hàng đợi RabbitMQ, trả về phản hồi 202 Accepted ngay trong 15ms.
    3. Tối ưu hóa dữ liệu & ORM: Giải quyết triệt để lỗi N+1 Query bằng @EntityGraph và đa hình hóa cấu trúc đề thi nhờ PostgreSQL JSONB."

2. Cấu Trúc Ngăn Xếp Công Nghệ (Tech Stack)

  • Ngôn ngữ & Nền tảng: Java 17 LTS, Spring Boot 3.x (Spring MVC, Spring Security).
  • Cơ sở dữ liệu chính: PostgreSQL 15+ (Lưu trữ quan hệ + Cột JSONB động).
  • Bộ nhớ đệm siêu tốc (In-Memory Data Store): Redis (Spring Data Redis Hash Template).
  • Message Broker: RabbitMQ (AMQP Protocol, Dead-letter handling).
  • Giao tiếp thời gian thực: Spring WebSocket STOMP qua SockJS.
  • Trí tuệ nhân tạo (AI Engine): Google Gemini Generative API (Tự động sinh đề + Retry Backoff).

PHẦN 2: PHÂN TÍCH ĐIỂM MẠNH & ĐIỂM YẾU CỤ THỂ

Mỗi kiến trúc phần mềm đều là một sự đánh đổi (Trade-off) có tính toán. Dưới đây là phân tích chi tiết các điểm mạnh vượt trội và những điểm giới hạn thực tế cần cải thiện:

Hạng Mục Điểm Mạnh Cụ Thể (Strengths) Điểm Yếu Thực Tế & Khắc Phục (Limitations & Mitigations)
1. Luồng Ghi & Auto-save Redis Hash O(1): Giảm 95% Disk Write I/O xuống PostgreSQL. Độ trễ ghi nhận đáp án < 3ms. Tính bốc hơi của RAM (Volatility): Nếu máy chủ Redis mất điện đột ngột có thể thất thoát đáp án tạm.
Khắc phục: Bật Redis AOF (everysec) + LocalStorage Sync.
2. Luồng Nộp & Chấm Bài RabbitMQ Event-Driven: Chịu tải nộp bài ồ ạt ở phút chót (Peak Submission). Phản hồi API 202 Accepted trong < 15ms. Chưa có Dead Letter Queue (DLQ): Bài làm dị tật có nguy cơ gây tắc vòng lặp Consumer nếu không bắt ngoại lệ triệt để.
Khắc phục: Cấu hình RabbitMQ DLX + Retry Policy 3 lần.
3. Truy Vấn Đề Thi (Read Flow) Fix N+1 bằng @EntityGraph: Tải đề thi 100 câu chỉ tốn duy nhất 1 câu SQL JOIN thay vì 101 câu query. Chưa có Read-through Cache: Hàng ngàn thí sinh cùng mở đề một lúc vẫn hit trực tiếp DB connection pool.
Khắc phục: Áp dụng @Cacheable cho API chi tiết đề thi.
4. Mô Hình Hóa Dữ Liệu PostgreSQL JSONB: Hỗ trợ đa dạng loại câu hỏi (kéo thả, điền từ, chọn 1, chọn nhiều) mà không cần đổi Schema bảng. Mất ràng buộc Foreign Key lỏng lẻo trong JSON: Khó áp dụng toàn vẹn tham chiếu cấp độ Database trên các object con.
Khắc phục: Kiểm soát chặt bằng Bean Validation / DTO.
5. Tích Hợp AI (Gemini) Sinh đề tự động + Auto-Retry: Tự động vượt qua lỗi 503 khi Google Server quá tải. Bảo mật API Key trong DB. Độ trễ phụ thuộc bên thứ ba (2-5s): Bị giới hạn Rate limit (15 RPM nếu dùng gói Free Tier).
Khắc phục: Chuyển sang Background Task + Hàng đợi sinh đề.

Chi Tiết 5 Điểm Mạnh Nổi Bật

1. Đột Phá Luồng Ghi Đáp Án Bằng Redis In-Memory (O(1)) Giảm 95% DB Load
Bản chất kỹ thuật: Dùng cấu trúc lệnh HSET exam:{userId}:{quizId} {questionId} {answer}.
Số liệu đo lường: Thời gian phản hồi mỗi click dưới 3ms. Hấp thụ thoải mái 5,000+ lượt click/giây trên 1 máy chủ thông thường.
Lợi ích thực tế: Thí sinh bấm chọn đáp án liên tục không gây Disk Write I/O trên PostgreSQL. F5 tải lại trang hay chập chờn mạng đều tự phục hồi đáp án nguyên vẹn từ RAM.
2. Hấp Thụ Tải Đột Biến Phút Chót Với RabbitMQ & WebSocket Non-Blocking
Bản chất kỹ thuật: Controller đóng gói ExamSubmittedEvent, ném vào Queue và trả ngay 202 ACCEPTED.
Số liệu đo lường: API nộp bài phản hồi trong 10 - 15ms. Worker chấm điểm tuần tự với throughput ổn định.
Lợi ích thực tế: Khi hết giờ thi, 1,000 thí sinh bị "Force Submit" cùng một giây. Hệ thống không bị treo hoặc chết Thread Pool như mô hình đồng bộ truyền thống. Điểm số đẩy về màn hình ngay lập tức qua WebSocket STOMP.
3. Triệt Tiêu Lỗi N+1 Query Bằng @EntityGraph 1 Query Duy Nhất
Bản chất kỹ thuật: Khai báo @EntityGraph(attributePaths = {"questions"}) trên QuizRepository.
Số liệu đo lường: Truy xuất đề thi có 100 câu hỏi: Giảm từ 101 queries xuống 1 câu query duy nhất (LEFT OUTER JOIN).
Lợi ích thực tế: Loại bỏ hoàn toàn hiện tượng nghẽn đường truyền giữa Spring Boot và PostgreSQL, tiết kiệm băng thông và tài nguyên CPU máy chủ cơ sở dữ liệu.
4. Thiết Kế Đa Hình Dữ Liệu Bằng PostgreSQL JSONB Zero Schema Migration
Bản chất kỹ thuật: Dùng @JdbcTypeCode(SqlTypes.JSON) lưu cấu trúc câu hỏi động và evidence lịch sử làm bài.
Lợi ích thực tế: Mở rộng thêm các dạng câu hỏi mới (Code editor, Audio listening, Matching pairs) trong tương lai mà không cần chạy lệnh ALTER TABLE hay can thiệp vào cấu trúc Database cũ.
5. Bảo Mật Stateless JWT & Cơ Chế AI Kháng Lỗi (Resilient AI) Stateless & Resilient
Bản chất kỹ thuật: JWT Filter + @PreAuthorize cô lập dữ liệu (Data Isolation). Thuật toán Auto-Retry với Exponential Backoff khi gọi Gemini.
Lợi ích thực tế: API Key lưu trữ trong DB (`system` table) thay vì hardcode trong file config. Người dùng thường không thể truy cập trái phép vào kết quả của thí sinh khác dù biết ID bài làm.

Chi Tiết 5 Điểm Yếu Thực Tế & Lộ Trình Khắc Phục

1. Rủi Ro Mất Dữ Liệu Tạm Khi Redis Crash (In-Memory Volatility) Mức độ: Cao
Thực trạng kỹ thuật: Redis Hash lưu đáp án tạm trên RAM. Nếu cấu hình mặc định (chỉ snapshot RDB mỗi vài phút) và container Redis gặp sự cố, các đáp án chưa kịp Submit có nguy cơ bị thất thoát.
Giải pháp khắc phục cụ thể:
1. Bật cơ chế appendonly yes kết hợp appendfsync everysec trong cấu hình Redis, đảm bảo tối đa chỉ mất 1 giây dữ liệu ghi nếu máy chủ sập nguồn.
2. Phía Client (React) tích hợp thêm tầng backup ngầm vào localStorage, tự động so sánh và đồng bộ lại nếu kết nối Redis bị đứt quãng.
2. Chưa Có Tầng Read-Through Cache Cho Đề Thi Mức độ: Trung bình
Thực trạng kỹ thuật: Hệ thống tối ưu xuất sắc luồng Ghi, nhưng luồng Đọc (khi 1,000 học sinh bấm "Bắt đầu làm bài" cùng giây thứ 0) vẫn query trực tiếp vào PostgreSQL Connection Pool.
Giải pháp khắc phục cụ thể:
Cài đặt cơ chế Cache-Aside với Spring Cache: @Cacheable(value = "quizzes", key = "#quizId") với TTL 10 phút. Toàn bộ thí sinh thi cùng một đề sẽ đọc dữ liệu tĩnh từ Redis, giảm tải hoàn toàn cho Database.
3. Chưa Có Dead Letter Queue (DLQ) & Rate Limiting Mức độ: Trung bình
Thực trạng kỹ thuật: Nếu bài nộp có định dạng JSON bị dị tật hoặc lỗi Runtime logic ở Consumer, message có thể bị requeue liên tục gây thắt nút cổ chai hàng đợi. Đồng thời chưa có Rate Limiter chống Spam click vào API Auto-save.
Giải pháp khắc phục cụ thể:
1. Cấu hình Dead Letter Exchange (DLX) trong RabbitMQ: Sau 3 lần retry thất bại, tự động chuyển bài thi lỗi sang hàng đợi riêng để Dev phân tích.
2. Tích hợp Bucket4j (Token Bucket) giới hạn mỗi thí sinh tối đa 5 request auto-save / giây.
4. Độ Trễ & Giới Hạn Quota Của API AI Bên Thứ Ba (Gemini) Mức độ: Thấp
Thực trạng kỹ thuật: Gọi LLM API có độ trễ tự nhiên từ 2 - 5 giây. Nếu dùng tài khoản Google Free Tier bị giới hạn 15 RPM (Requests per minute), dễ gặp HTTP 429/503 nếu tạo đề liên tục.
Giải pháp khắc phục cụ thể:
Chuyển tính năng sinh đề AI thành Background Job không đồng bộ: Admin gửi yêu cầu -> nhận Job ID -> AI sinh xong bắn thông báo qua WebSocket thay vì giữ kết nối HTTP chờ đợi.
5. Kiến Trúc Single-Node Docker & Thiếu Metrics Giám Sát Mức độ: Trung bình
Thực trạng kỹ thuật: Hệ thống hiện tại triển khai trên 1 node Docker Compose duy nhất (Single Point of Failure). Chưa có Dashboard hiển thị biểu đồ tải thời gian thực.
Giải pháp khắc phục cụ thể:
Lộ trình nâng cấp: Bổ sung Prometheus + Grafana để theo dõi RabbitMQ Queue Depth và Redis Memory Usage. Khi quy mô trường đại học lớn (> 50,000 học sinh), tách thành Microservices và deploy trên Kubernetes (K8s).

PHẦN 3: KỊCH BẢN DEMO THỰC TẾ TRÊN MÀN HÌNH

Kịch bản 1: Xác Thực JWT & Cô Lập Dữ Liệu (Data Isolation)

  • Thao tác: Đăng nhập tài khoản thí sinh `student1` -> Truy cập trang xem kết quả. Thử sửa ID trên URL để xem kết quả của `student2`.
  • Thuyết minh:
    "Hệ thống áp dụng cơ chế bảo mật Stateless JWT kết hợp kiểm soát dữ liệu chặt chẽ ở tầng Service: Thí sinh chỉ được quyền truy xuất duy nhất lịch sử thi của chính mình. Mọi hành vi sửa ID trên request đều bị chặn đứng bởi @PreAuthorize và trả về mã lỗi 403 Forbidden."

Kịch bản 2: Admin Tạo Đề Tự Động Bằng AI & Kháng Lỗi (Gemini)

  • Thao tác: Đăng nhập quyền `admin` -> Vào module Tạo Đề Thi -> Nhập chủ đề: "5 câu hỏi về Lịch sử Việt Nam thế kỷ 20" -> Nhấn "Tự động sinh đề bằng AI".
  • Thuyết minh:
    "Tại đây, Backend gọi đến Google Gemini API với logic bóc tách JSON và tự động lưu thẳng vào bảng questions. Đặc biệt, API Key được load động từ Database bảng system, mã nguồn hoàn toàn sạch không bị lộ Key bí mật. Đồng thời có thuật toán Retry thông minh tự động vượt qua lỗi 503 khi server AI bận."

Kịch bản 3: Thí Sinh Làm Bài & Auto-Save Tốc Độ Cao (Redis Hash O(1))

  • Thao tác: Đăng nhập `student1` -> Bắt đầu làm bài thi -> Click chọn đáp án các câu 1, 2, 3 liên tục. Mở Terminal / Redis-CLI gõ lệnh: HGETALL exam:1:1 để xem dữ liệu ghi tức thì trên RAM.
  • Thuyết minh:
    "Mời quý thầy cô / anh chị quan sát màn hình Terminal: Ngay khi em click chọn đáp án, hệ thống tuyệt đối không gọi lệnh UPDATE xuống PostgreSQL. Toàn bộ dữ liệu được ghi đệm vào Redis Hash với độ trễ dưới 3 mili-giây. Dù thí sinh có vô tình tắt trình duyệt hoặc F5 tải lại trang, bài làm vẫn được bảo lưu 100% từ RAM." 💡 Điểm nhấn phản biện: "Đây chính là vũ khí giúp hệ thống chịu tải hàng ngàn học sinh cùng click đáp án mà không làm tê liệt ổ cứng Database."

Kịch bản 4: Nộp Bài Bất Đồng Bộ (RabbitMQ) & Bắn Điểm Real-Time (WebSocket)

  • Thao tác: Nhấn nút "Nộp bài" (Submit) -> Màn hình lập tức báo "Đã nhận bài làm" (HTTP 202). Quan sát 1-2 giây sau, một thông báo Toast dạng popup tự động nhảy lên góc phải kèm điểm số và kết quả.
  • Thuyết minh:
    "Khi em bấm nộp bài, API trả về ngay lập tức mà không bắt học sinh phải chờ chấm điểm. Một Event bài nộp đã được ném vào RabbitMQ. Ở background, tiến trình chấm điểm diễn ra song song và ghi kết quả vào PostgreSQL. Ngay khi hoàn tất, hệ thống tự động bắn một WebSocket message về trình duyệt của học sinh để hiển thị điểm số tức thì."

Kịch bản 5: Chứng Minh Tối Ưu N+1 Query Bằng Hibernate SQL Log

  • Thao tác: Mở tab Console Backend trong IDE -> Thí sinh mở đề thi gồm hàng chục câu hỏi -> Xem log Hibernate sinh ra đúng duy nhất 1 câu SQL `LEFT OUTER JOIN`.
  • Thuyết minh:
    "Trong JPA thông thường, việc truy vấn 1 đề thi có 50 câu hỏi sẽ phát sinh 51 câu query con (N+1 Query). Nhờ khai báo @EntityGraph, em đã ép Hibernate tối ưu thành đúng 1 câu SQL duy nhất, bảo toàn hiệu năng tối đa cho hệ thống."
